1项目概览

一个单 HTML 文件的纯前端工具：用户上传若干二维码图片，工具为每张原图生成一张 A4 幅面、重复铺满该二维码的 PNG，并按文件夹分组打包为 ZIP 下载。

项值
产物文件qrcode-a4-layout.html（单文件，含 HTML + CSS + JS）
代码规模约 1375 行（其中 JS 约 950 行）
外部依赖零。无 CDN、无框架、无 npm 包、无字体文件
网络请求零。完全离线可用
运行环境任何支持 ES2020 的浏览器；实测 Chrome / Edge
构建步骤无。源码即产物，双击即可运行
模块化单个 IIFE，"use strict" 作用域隔离
架构一句话总结：无状态 UI 层 + 集中式 state 对象 + 三个渲染入口（drawA4 供预览/缩略图复用，renderFull 供 300DPI 导出）+ 自研 ZIP 打包器。

2设计原则与约束

  1. 单文件交付：用户只需拷贝一个 .html，无安装、无依赖、无构建。这是本文档最重要的约束 —— 任何引入外部库的改动都应被否决，除非收益极大。
  2. 离线优先 / 隐私优先：图片全程不离开浏览器。禁用一切网络调用（fetch、XMLHttpRequest、外链资源）。
  3. 厘米为准的心智模型：所有参数、常量、公式一律以厘米为单位，仅在真正绘制时换算成像素。避免"像素信仰"导致的打印尺寸漂移。
  4. 单一真相源：所有可交互状态集中在 state，DOM 只作展示。任何参数变更走 readXxx() → renderXxx() 的单向流。
  5. 三条渲染路径口径一致：预览、缩略图、导出必须用同一套排版常量与同一套定位公式，否则会出现"预览好看、导出跑偏"。这是项目中最容易出 bug 的地方，改动时务必交叉验证。
  6. 降级而非报错：CompressionStream 不可用 → 存储模式；actualBoundingBox 不可用 → 1.16em 兜底；拖拽取不到路径 → _relPath 兜底。

4状态模型 state

const state = {
  files: [],      // [{ id, file, name, url, img, groupId }]  已加载的图片项
  groups: [],     // [{ id, name, key, fileIds }]           分组（导出粒度）
  current: 0,     // 当前预览的 files 索引
  params: { w:3, h:3, gapX:0.5, gapY:0.5 },                       // 单位 cm
  title:  { on:true, src:"filename", text:"", prefix:"",
            suffix:"", pos:"top", sizeMM:14 },            // 字号单位 mm
  zoom:   { mode:"fit", factor:1 },   // fit | manual | actual
  titleTouched: false  // 用户是否手动改过"导出文件名"，改过则锁定，导入时不再自动覆盖
};
let uid = 0;   // 文件项自增 id
let gid = 0;   // 分组自增 id
字段说明
files[].urlURL.createObjectURL(f) 产生的 blob URL。移除/清空时必须 revokeObjectURL，否则内存泄漏。
files[].img已 onload 完成的 HTMLImageElement，可直接 drawImage。
files[].groupId冗余字段，指向所属组；导出时按它过滤。
groups[].key完整相对路径（如 主文件夹/子A），用于唯一匹配组。不同于 name（仅末段，可能重名）。

⚠️ 不变量：state.files 的顺序必须与 groups 中 fileIds 的拼接顺序一致。这个不变式由 syncGroups() 维护，任何直接增删 state.files 的代码都必须随后调用它。

5排版算法详解

5.1 常量

const A4_W_CM = 21.0, A4_H_CM = 29.7;   // A4 物理尺寸
const MARGIN_CM = 1.0;                       // 四周安全边距
const PRINT_DPI = 300;                      // 导出分辨率
const PREVIEW_PX_PER_CM = 26;               // 预览基准比例
const GAP_FALLBACK_CM = 0.3;                 // 自动缩小时的保底最小间距
const TITLE_TOP_CM = 0.6;                    // 标题距【物理】上/下边缘
const TITLE_GAP_CM = 0.5;                    // 标题与首/末行二维码间距
const CM_PER_INCH = 2.54;

5.2 容量计算 calcLayout

// 水平：可用宽 = 21 - 1*2 = 19cm
// 垂直：可用高 = 29.7 - 1*2 - titleBandCm()

function calcLayout(){
  const availW = A4_W_CM - MARGIN_CM*2;
  const availH = A4_H_CM - MARGIN_CM*2 - titleBandCm();
  const cols = Math.floor((availW + gx) / (w + gx));   // 首尾不留间距的经典公式
  const rows = Math.floor((availH + gy) / (h + gy));
  return { cols, rows, total: cols*rows, availW, availH };
}

公式推导：n 个格子 + (n−1) 个间距 ≤ availW，即 n·w + (n−1)·gx ≤ availW。解得 n ≤ (availW + gx)/(w + gx)，向下取整。

5.3 标题占用高度 titleBandCm

用于容量估算（只关心"扣掉多少高度"，不关心具体像素）：

function titleBandCm(){
  if(!t.on) return 0;
  // 内容 = 距上边缘0.6 + 字形高 + 与二维码间距0.5
  // 但 0.6cm 已经落在 1cm 安全边距内部，所以只需额外扣 (0.6 + 字高 + 0.5 - 1)
  const glyphCm = (t.sizeMM/10) * 1.16;   // 1.16em ≈ 汉字字面高
  return TITLE_TOP_CM + glyphCm + TITLE_GAP_CM - MARGIN_CM;
}
⚠️ 这里用 1.16em 近似字高，而实际绘制用 actualBoundingBox 精确测量。两者理论上可能差几个像素，但因为 availH 还有余量，且 rows 取整，实测不会导致越界。这是刻意的近似，不要试图"修"它。

5.4 极端参数兜底 resolveLayout

当 calcLayout().total < 1（放不下）时，以 0.95 的比例迭代缩小尺寸/间距，最多 80 轮，直至至少能放 1 个：

for(let i=0; i><80 && (放不下); i++){
  if(横向仍放不下){ w *= 0.95; if(gx > GAP_FALLBACK_CM) gx *= 0.95; }
  if(纵向仍放不下){ h *= 0.95; if(gy > GAP_FALLBACK_CM) gy *= 0.95; }
}
  • 收敛性：0.95^80 ≈ 0.016，即最多缩到原尺寸的 1.6%，必然放下，不会死循环。
  • 返回值带 scaled:true 标记，导出路径据此改用缩放后的尺寸（保证导出与预览一致）。
  • 同时通过 updateNotice() 向用户显示黄色提示。

5.5 单位换算

// 厘米 → 像素（按指定 DPI）
function cmToPx(cm, dpi){ return Math.round(cm / 2.54 * dpi); }

// 300 DPI 下 A4 画布尺寸
// 2480 × 3508 px    (21/2.54*300 = 2480.3 → 2480)

// 每厘米对应像素（导出用）
const pxPerCm = PRINT_DPI / 2.54;   // ≈ 118.11 px/cm

核心绘制循环（以 renderFull 为例）

// 1. 标题下方起点
contentTop = titleTopY + glyphH + pxPerCm * TITLE_GAP_CM;   // titleTopY = 0.6cm
contentH   = pxPerCm*A4_H_CM - contentTop - m;              // 底部仍留 1cm

// 2. 网格对齐：水平居中，垂直【靠上】
offX = m + Math.max(0, (contentW - usedW) / 2);
offY = contentTop;                          // 不居中！余量全部留在底部

// 3. 双重循环绘制
for(r…) for(c…) drawContain(ctx, img, offX + c*(w+gx), offY + r*(h+gy), w, h);

等比绘制 drawContain

function drawContain(ctx, img, x, y, bw, bh){
  const s = Math.min(bw/iw, bh/ih);          // 取小 → contain
  const dw = iw*s, dh = ih*s;
  const dx = x + (bw-dw)/2, dy = y + (bh-dh)/2;   // 格子内居中
  ctx.drawImage(img, dx, dy, dw, dh);
}

用 Math.min 而非 Math.max：前者是 contain（完整放入、可能留白），后者是 cover（填满、可能裁切）。二维码必须 contain，否则会被切掉定位角。

三路径一致性验证（实测）

默认参数（3×3cm / 间距 0.5 / 字号 14mm）下，三条路径的 contentTop 均为 2.724 cm（= 0.6 + 字形高 1.624 + 0.5），完全对齐。验证脚本见第 15 节。

7标题排版与字形测量

7.1 为什么不直接用 fontPx × 1.35

Canvas 的 font 尺寸是"行高"概念，不等于汉字实际可见高度。用行高估算会在标题下方留下约 0.35em 的多余空白（用户实测反馈过）。

7.2 titleGlyphHeight —— 精确测量

function titleGlyphHeight(ctx, fontPx){
  const prevFont = ctx.font;
  const m = ctx.measureText("中文Ag");   // 同时覆盖 CJK 与拉丁
  let h = 0;
  if(m.actualBoundingBoxAscent !== undefined){
    h = m.actualBoundingBoxAscent + (m.actualBoundingBoxDescent || 0);
  }
  ctx.font = prevFont;
  if(!h || !isFinite(h)) h = fontPx * 1.16;   // 兜底
  return h;
}
  • 调用前提：ctx.font 必须先设好目标字体，否则测的是上一次的字体。
  • 测量样本用 "中文Ag"：汉字决定 ascent，含下伸部的拉丁字母决定 descent。
  • textBaseline = "top" 时，fillText(text, x, topY) 的 topY 是行框顶部，字形实际从 topY + ascent 处开始。因此"字形底边"= topY + ascent + descent = topY + h。

7.3 标题定位公式

位置标题 topY内容区 contentTop
顶部pxPerCm × 0.6titleTopY + glyphH + pxPerCm×0.5
底部canvasH − pxPerCm×0.6 − glyphHm（正文从 1cm 起）

注意：顶部的 0.6cm 从物理上边缘量起，不是从 1cm 安全边距量起。这是历史 bug 的修复点（曾误写为 m + 0.6cm，实际变成 1.6cm）。

8分组模型与文件夹导入

8.1 分组键 groupKeyOf

function groupKeyOf(f){
  const p = f.webkitRelativePath || f._relPath || "";
  if(!p) return "";
  const parts = p.split("/").filter(Boolean);
  parts.pop();                              // 去掉文件名
  if(parts.length===1) return parts[0];            // 主文件夹下直接是图
  return parts[0] + "/" + parts[1];              // 主文件夹/第一层子文件夹
}

语义：以「主文件夹 / 第一层子文件夹」为分组粒度，更深的层级并入所在的第一层子文件夹。

输入路径分组键
主/a.png主
主/子A/b.png主/子A
主/子A/更深/c.png主/子A
主/子B/d.png主/子B

为什么不用 parts[0] 单层？那样会把 主/ 下所有子文件夹并成一组，用户实测反馈过"导入进去的没有按文件夹分组"。

为什么不用「完整路径」作键？"主/子A/更深"与"主/子A"会分裂成两组，用户期望的是按可见的第一层归类。

8.2 组名 displayNameOf

取 key 的末段作为组显示名（ZIP 命名用）。例如 主/子A → 子A。

当不同主文件夹下有同名子文件夹（如 甲/门店 与 乙/门店），name 会重名。此时：

  • 组匹配用 key（唯一）而非 name，避免误合并；
  • renderFileList 检测到重名时，表头改为显示完整 key 以便区分；
  • ZIP 命名冲突时自动加 (2) (3)。

9ZIP 打包器实现

为了让单文件工具保持"零依赖"，ZIP 是按 PKZIP APPNOTE 规范手写的。

9.1 结构

[本地文件头 LFH] [文件数据] [本地文件头 LFH] [文件数据] … [中央目录项 CDH] × N [中央目录结束记录 EOCD]

9.2 关键字段

字段值说明
LFH 签名0x04034B50"PK\3\4"
CDH 签名0x02014B50"PK\1\2"
EOCD 签名0x06054B50"PK\5\6"
通用标志位0x0800bit 11 = UTF-8 文件名，中文名必需
压缩方法8 deflate / 0 store按 CompressionStream 可用性选择
版本需求202.0（支持 deflate）

9.3 CRC32

// 标准 IEEE 802.3 多项式 0xEDB88320（反射形式），查表法
const CRC_TABLE = (()=>{ /* 256 项预计算 */ })();
function crc32(buf){
  let c = 0xFFFFFFFF;
  for(let i=0; i<buf.length; i++) c = CRC_TABLE[(c ^ buf[i]) & 0xFF] ^ (c >>> 8);
  return (c ^ 0xFFFFFFFF) >>> 0;
}

9.4 压缩 deflateRaw

async function deflateRaw(buf){
  if(typeof CompressionStream === "undefined") return null;   // 触发回退
  const cs = new CompressionStream("deflate-raw");
  const w = cs.writable.getWriter();
  w.write(buf); w.close();
  const ab = await new Response(cs.readable).arrayBuffer();
  return new Uint8Array(ab);
}
⚠️ 必须用 "deflate-raw"（裸 deflate，无 zlib 头尾），不能用 "deflate"（那是 zlib 格式，带 2 字节头 + 4 字节 Adler-32，ZIP 会解压失败）。

失败或不可用时返回 null，buildZip 自动改用 method=0 存储模式，ZIP 依然合法可解压，只是体积大些。

9.5 时间戳 dosDateTime

const time = (hour<<11) | (min<<5) | (sec/2);      // 秒只有 5 bit，精度 2 秒
const date = ((year-1980)<<9) | ((month+1)<<5) | day;  // 年份从 1980 起算

9.6 偏移量累计

offset += localHead.length + stored.length;   // 中央目录需记录每个 LFH 的起始偏移

此处必须累计压缩后长度（stored.length），不是原始长度。

10预览缩放系统

实现方式：CSS 缩放

elPaper.style.width  = targetW + "px";
elPaper.style.height = (targetW * A4_H_CM / A4_W_CM) + "px";
/* canvas 保持 width:100%; height:100%，由浏览器做重采样 */

优点：缩放时不重绘 canvas，切换极快、无闪烁。
代价：放大超过 1 倍时预览会变模糊 —— 因为 canvas 内部像素分辨率固定（546×772）。这是刻意取舍，预览只作参考，真正精度以导出为准。

fitWidthPx 的计算

const avail  = Math.max(160, stage.clientWidth - 44);        // 44 = stage 内边距
const availH = Math.max(160, window.innerHeight - 220);     // 220 ≈ 其它 UI 高度估算
return Math.min(avail, availH * (A4_W_CM/A4_H_CM));              // 宽高都别超

窗口 resize 时，仅当处于 fit 模式才自动重算。

"1:1 实际尺寸"的精度说明

基于 CSS 规范 1in = 96px 的物理单位换算，但实际屏幕物理密度由操作系统缩放、显示器 PPI 决定，因此只能作参考量级，不能当尺子。此限制已在用户手册第 7 节说明。

11性能分析与量级

11.1 内存

对象量级
单张 300DPI A4 canvas 位图2480 × 3508 × 4B ≈ 33.2 MB
PNG 编码后（二维码黑白）约 50 ~ 300 KB / 张
200 张的 PNG 数据累积约 30 MB
✅ 为什么不会 OOM：导出循环是串行的 —— 每次只创建 1 张 33MB 的 canvas，编码成 PNG 后 canvas 即被 GC 回收，只保留几十 KB 的 PNG 字节。
反面教材：若改成 Promise.all 并行，16 核机器会同时开 16 张 33MB canvas ≈ 530MB，且每张都要走完整的 2480×3508 绘制 + PNG 编码（CPU 密集），反而更慢且可能崩。这就是串行的原因。

11.2 时间

  • 单张渲染 + PNG 编码：数十毫秒 ~ 数百毫秒（取决于机器与图中二维码密度）
  • 100 张：约十几秒到一分钟（进度条按张数线性推进）
  • 缩略图全量重绘：100 张 × 35 次 drawImage（68×96 小画布）≈ 毫秒级

11.3 主线程阻塞

导出循环虽然 await 了 toBlob，但每次绘制是同步的，会短暂占用主线程。靠 setOverlay() 强制重排 + await 让出事件循环，进度条得以刷新。未使用 Web Worker（因为 HTMLImageElement 不便跨线程传输，收益不划算）。

11.4 已识别但可接受的浪费

  • renderThumbs() 每次切图都全量重建所有缩略图，而非只更新选中态。100 张时多做了 99 次无用绘制，但总量仍毫秒级。
  • 缩略图内每张都调一次 resolveLayout()，纯计算，无压力。

13.2 潜在风险点

风险评估
参数上限偏宽松（qrH 最大 28cm、gap 最大 10cm）会触发 resolveLayout() 自动缩小。已收敛，非 bug。若要收紧可把 max 调小。
超大原图（>4000×4000）单张编码可能 1~2 秒，用户体验靠进度条缓冲。可考虑先降采样。
titleBandCm() 的 1.16 近似 vs 实际字形测量理论误差 < 1px（300DPI 下约 0.008cm），被取整吸收。已实测一致。
renderPreview() 空态提前 return 不调 applyZoom()设计选择，无 canvas 无需缩放。且 applyZoom 首行有判空保护。
titleGlyphHeight 内局部变量 m 与外部边距 m 同名作用域隔离，无实际冲突。可读性问题。

14扩展指南

14.1 新增一个排版参数（例：水平居中偏左）

  1. HTML：在「② 排版参数」加输入框，赋唯一 id。
  2. JS 常量/状态：state.params 加字段。
  3. readParams() 加读取 + clampNum() 范围限制。
  4. 事件绑定：加入 [elW,elH,…] 数组。
  5. 关键：drawA4() 和 renderFull() 两处都要改定位公式。
  6. 用第 15 节的验证脚本交叉比对两条路径的计算结果。

14.2 新增导出格式（例：JPEG）

canvasToBlob(cv, "image/jpeg", 0.92)   // 改类型与质量参数
// 注意同步修改 ZIP 条目扩展名 .png → .jpg

若同时支持两种格式，ZIP 中可能出现同名不同扩展名的条目 —— 现有去重逻辑按完整文件名比对，可正确处理。

14.3 修改分组粒度

只改 groupKeyOf() 的返回策略即可，其它逻辑（displayNameOf / 组匹配 / ZIP 命名）会自动适配。改完务必用第 15 节的四场景测试验证。

14.4 代码风格约定

  • IIFE + "use strict"，不用模块系统
  • DOM 引用统一在顶部 elXxx 批量声明
  • 所有数值参数一律 clampNum() 后写入 state
  • 不引入外部依赖（除非绝对必要）
  • 渲染函数保持"读 state → 输出"的纯函数姿态，不在渲染里改 state

const PREVIEW_PX_PER_CM=26, PRINT_DPI=300;

function contentTopCm(pxPerCm, sizeMM){
  const fontPx = (sizeMM/10) * pxPerCm;
  const glyph  = fontPx * 1.16;              // 兜底口径
  return TITLE_TOP_CM + glyph/pxPerCm + TITLE_GAP_CM;
}
console.log( contentTopCm(PREVIEW_PX_PER_CM, 14) );   // 预览
console.log( contentTopCm(3.24, 14) );               // 缩略图

// 三者应输出同一值 2.724
